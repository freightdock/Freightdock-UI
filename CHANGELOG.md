# Patch notes

Everything that changed in Freightdock, newest first. This file is compiled into the binary and is what the **Patch notes**
page in the app shows.

Format: `## [version] - date`, or `## [version] - first day to release day` for a release made over several days, then
`### Added`, `### Changed`, `### Security`, `### Performance`, `### Stability`, `### Fixed` or `### Removed` with one
bullet per change. Security is something somebody could have misused, Performance something that got quicker or lighter,
Stability something that can no longer crash, halt, leak or lose data, Fixed something that gave a wrong answer. An
`x.y.0` release carries a short title line under its heading: that title is what the app uses as the headline of the
whole series.

## [1.0.0] - 2026-11-09 to 2026-11-10

First light
- **Your picture from your sign-in provider** in the menu: Authentik's (or any OpenID provider's) picture, fetched and kept by Freightdock so your browser never calls Gravatar, with nothing painted behind it.
- **Account says how you sign in**: an `SSO: Authentik` badge (or the directory's) beside your role. An account signed in through a provider shows no password, two-factor or "Link to" card, since the provider looks after all three; a directory account keeps two-factor.
- **A new webhook runs at once** even when it takes the place of one just removed; it used to wait out the old one's ten seconds and answer 429.
- **The phone menu's More sheet** no longer shows the word "null" above its pages (FinUI wrote a missing search box as text).
- **Rolling a Swarm service back, scaling it or updating it, or draining, promoting or labelling a node, on a busy host** no longer fails with "update out of sequence": Swarm moves their versions by itself, so the change is read and sent again. An update over somebody else's change meanwhile is refused instead of overwriting it.

### Added
- **A dashboard**, where Freightdock now opens: gauges for the managers online, the quorum and its leader, and the workers healthy; the CPU and memory used over the whole cluster; and a row per node with its CPU, memory, disk and workloads.
- **The cluster network on the pages**: every workload shows its internal address (on the Cluster stacks page and on its node's page), each stack its network, and each node whether its overlay is up, waiting or failing (and why), with its WireGuard key.
- **Name a manager, and open its page**: click a manager on the Cluster page (or the leader on the dashboard) to see its address, its place in Raft, whether it is heard and the workers connected to it; an administrator gives it a name there, shown in Freightdock instead of its address.
- **A page for every node**: click a node on the Cluster page to see what the managers know of it, the stacks' workloads placed on it and the containers it says it runs.
- **Managers and workers**: the Cluster page shows which node each manager runs on, and whether each node runs a manager too.
- **Rename a node** in Freightdock only: an administrator gives it a name to be shown by, while the node and the cluster keep its hostname. Written to the activity log.
- **The managers run the UI**: `freightdock-manager ui <image>` places it on a node of the cluster, moves it when that node fails, and every manager answers for it at port 7443, so any manager's address opens it. Its token and the cluster CA come in `FREIGHTDOCK_CLUSTER_TOKEN` and `FREIGHTDOCK_CLUSTER_CA` (the values, beside the `_FILE` settings), and the CA of its own certificate travels with its database, so the certificate you trusted once is still trusted after a move.
- **Freightdock**: one small Rust binary with its web UI built in, managing Docker without a licence key, a node limit or a paid tier.
- **Forgejo and Gitea registries**: your own git server's packages as a registry of its own kind, asking for its address and an access token with the package scopes, browsed and pulled from like any other.
- **Ready-made images** for Freightdock and its agent, for amd64 and arm64: `:latest` and `:X.Y.Z` from every release, `:edge` from every change to `main`, so installing Freightdock is a `docker run` or a `docker compose up -d` and no build. The Freightdock image names its own agent's image, so the line it shows for a new host pulls the agent that matches.
- **HTTPS from the first start**, with a self-signed certificate made and kept in the data folder; bring your own with `FREIGHTDOCK_TLS_CERT` and `FREIGHTDOCK_TLS_KEY`, or run plain HTTP behind a proxy with `FREIGHTDOCK_TLS=off`.
- **The first administrator** is made on the first visit, with the setup token `docker exec freightdock freightdock setup-token` prints (it is in the log too, and the same across restarts until setup is done), and the local Docker is already there as the first environment. A command `freightdock` does not know (`freightdock --help` lists them) is refused rather than starting a second Freightdock that prints a setup token of its own.
- **Single sign-on with OpenID Connect** (Authentik, Keycloak, Entra ID and the rest): `freightdock-write` makes an administrator, `freightdock-read` a user, anybody else is turned away, and the role follows the groups at every sign-in. The password sign-in stays beside it for when the provider is down.
- **Containers**: list, start, stop, restart, kill, pause, rename, remove; make one from Docker's own options, edit one (it is replaced, and put back if the new one fails), recreate one from a freshly pulled image; follow its logs, open a console inside it, watch its CPU, memory, network and disk live.
- **Images**: list with what uses them, pull, tag, push, build from a Dockerfile, a tar or a Git address, load and export, remove and prune.
- **Volumes and networks**: list with who uses them, make, inspect, remove and prune; connect containers to networks and take them off again.
- **Events** as they happen, and the disk Docker uses by kind, with one prune for everything.
- **The activity log**: every change made through Freightdock, with who, what, which and from where.
- **Appearance in Settings**, as FinStats has it: paste a preset code made at FinUI create (or the address or install line that holds it), see what it picks, and Freightdock wears it for everybody from the first paint. A link takes you to FinUI create to make one or change it.
- **A code editor** for Dockerfiles on the build page, and for a stack's or a template's compose file and `.env`: line numbers, highlighting, undo, search and bracket matching, in Freightdock's colours in both themes.
- **Attach to a container's main process** from its Console tab, beside running a command: see what it prints and type into it. Leaving never stops it, and a container whose input would close on leaving is only watched.
- **Home**: every host on one page, the first thing after signing in: up or down, Docker and agent versions, where it is, its group and tags, and what it holds (containers running, nodes, cores, memory, images, volumes, stacks). Count, filter, sort and search them; a host that is down shows what it last had, and a slow one never holds the page up. Choose one to work on it.
- **Environment groups and tags**: put each host in a group and give it tags, to find it and, as roles come, to give people access to a whole group at once.
- **Networks from the container's page**: connect it to another network, with aliases or an address of its own, and take it off one, while it runs.
- **Patch notes**, this page, with a dot in the menu when Freightdock has been updated since you last read it.
- **Many hosts**: add other Docker hosts under Environments and pick one on Home; each shows whether it is up, its Docker version and when it last answered.
- **The agent**, `freightdock-agent`: run one `docker run` line on a host and Freightdock manages its Docker. The agent dials out to Freightdock, so nothing on the host is opened to the network and it works from behind NAT; it comes back by itself after a break.
- **TLS hosts**: reach a Docker that listens on its TLS port (2376) with a client certificate you paste in.
- **Stacks**: write a compose file and its `.env` variables, then deploy, update, stop, start, pull and redeploy, or remove it (its volumes too, if you like), with Docker Compose's own output as it goes. Compose itself does the work, so a stack behaves as it would on the command line, on any environment (an agent's host or a TLS host as well as the local one); the image bundles a pinned, checksum-verified Compose.
- **Git stacks**: a repository, a branch or tag, the compose file's path, and a token for a private one (kept sealed). Freightdock checks the branch every few minutes and deploys again when it moved, and says on the stack's page how the last check went.
- **App templates**: Portainer's template lists (v2 and v3) work as they are, Portainer's own to begin with and any others you add in Settings; deploy a container or a stack with the variables it asks for. Write custom templates of your own: a compose file and the variables to ask.
- **Webhooks** for CI: an address that redeploys a stack (from its Git branch as it is now, images pulled again) or pulls a container's image and recreates it. No sign-in, so the address is the key: it is shown once and kept only as a hash.
- **Stacks started elsewhere** (on the command line, by Portainer) are listed as external, and can be adopted: Freightdock reads their files where they were started, with relative paths made absolute and variables left as `${...}`.
- **Registries**: save your sign-in for Docker Hub, GitHub (ghcr.io), GitLab, Amazon ECR, Quay or any other registry, tested as you save it, and every pull, push, container made from an image there and stack deployed with Compose signs in by itself; ECR's access keys are swapped for its short-lived token for you.
- **A registry browser**: a registry's repositories and their tags (your Docker Hub account's or an organisation's), and pull a tag onto the host you are on with one click.
- **API tokens** in your Account page, for scripts and AI agents: named, shown once, read-only if you like, good for a set number of days or until you revoke them, and each shows when it was last used. A token acts as you, and the activity log says which token made a change.
- **An MCP server for AI agents** at `/mcp`: connect Claude Code (the Account page has the line to paste) and it can list your hosts, containers, images, volumes and networks, read logs, stats and the activity log, start, stop, restart, kill, make and remove containers, run commands in them, and pull and remove images, as you and no more. A read-only token lets it look and nothing else.
- **Swarm**: on a host that manages a swarm, a Swarm group in the menu: the cluster at a glance, its nodes (drain, pause, promote, demote, label, remove), services (create, update, scale, roll back, remove, their tasks and their logs as they come), secrets and configs, and stacks deployed with `docker stack deploy`, their Compose file kept to change and deploy again.
- **Image updates**: a badge on every container and image whose tag has a newer image in its registry, checked by digest (multi-arch images included) without pulling and at most every six hours a registry. Update one from its page, or let it update itself: give it the `freightdock.auto-update=true` label, or flip its switch, and Freightdock pulls the new image, makes it again with the same settings, and puts the old one back if the new one does not stay up. Images on a registry you saved are checked and pulled signed in.
- **Notifications**: hear through a webhook, e-mail, ntfy or Gotify when a container dies or turns unhealthy, a newer image is out, a stack does not deploy, or a host stops answering, each channel with the events it wants and a Test button. A container crashing in a loop is one message, not one a minute, and a stop you asked for is no news.
- **Volume files**: browse a volume's folders, download a file (or a folder as a tar), upload files, make folders and delete, from the Volumes page, on any host: local, TLS or an agent's. Administrators only, and every change is in the activity log.
- **Backups of Freightdock itself**: the database, its keys, the agents' CA and the stacks' files, sealed with your passphrase, to a folder or any S3-compatible store, on a schedule, the oldest beyond what you keep removed. Restore from the Backups page (Freightdock starts itself again with it in place, and keeps what it replaced) or, with Freightdock stopped, `freightdock restore <archive>`.
- **Resource history**: a container's CPU, memory, network and disk over the last hour, day, week or month, on its History tab, sampled every minute on every host and kept for a week (both set in Settings). It follows the container by name, so an edit or an update does not start it again.
- **Live stats at your pace**: a container's Stats tab samples every 5 seconds, or every 1, 10 or 30 if you pick it, and remembers the choice in this browser; network speed stays per second whatever the pace.
- **Users and teams** in Settings: make local users with a password, rename, disable and enable them, give a new password, remove them, and see when each last signed in and whether they come through SSO; put them in teams. Change your own password in Account.
- **Roles as Portainer Business has them**, given to a person or a team on one environment or on a whole group: Environment administrator, Operator (start, stop and consoles, but nothing made or removed), Helpdesk (reads everything, no console), Standard user (makes things and manages their own) and Read-only user. A host you have no role on is not shown to you, and the pages hide what your role cannot do.
- **Ownership** of containers and stacks: public, a team's, or yours. What you make is yours unless you share it; Standard and Read-only users see the public ones, their teams' and their own.
- **The auth log** in Settings: every sign-in and failed one, sign-out, SSO sign-in turned away and API token use, with who, from where and in what browser, filtered by kind, person and time.
- **CSV export** of the activity log and the auth log.
- **Link your account to single sign-on** from Account, and sign in through the provider from then on.

- **Import from Portainer** (Settings): connect with Portainer's address and an access token, and Freightdock reads what Portainer has through its API, changing nothing there. Its environments are matched to Freightdock's by their Docker engine, with a preview of everything found and what it would become; then the stacks you tick are adopted in place, under the same project name, so their containers keep running, with their variables and `stack.env`; Git stacks come as Git stacks, polled as before. Groups and tags land on the matched hosts, registries come with their user (give the password after: Portainer never hands it out), custom templates too. Each thing says whether it was done, skipped or failed, and why, and importing again makes nothing twice.
- **AI agents (MCP) in Settings**: switch the MCP server on or off for the whole instance (on, as before), see its address and the line that connects Claude Code, every API token with whose it is and when it was last used, and revoke any of them; each person still makes their own token in Account.
- **A certificate authority to trust**: Freightdock's own HTTPS certificate is now signed by a small CA of its own, kept in the data folder. Download it from Settings or Account (or `/api/tls/ca.pem`), trust it once, and browsers, curl and Claude Code (`NODE_EXTRA_CA_CERTS`) check Freightdock's certificate without a warning; the page says how on Linux, macOS, Windows and Firefox.
- **A stack's Environment tab**: every service's variables as the next deploy gives them, with `.env`, `env_file` and `${...}` defaults filled in, so settings kept in the compose file show too; passwords and tokens stay hidden until you press Show, and only those who may read the stack see it at all.
- **Teams from Portainer**: the import previews each of Portainer's teams, whether it would be made or is in Freightdock already (by its name, or because an earlier import made it), and which of its members would join, so a team comes with the people Freightdock has an account for, matched by name; those Freightdock has no user for are named and left out. Importing again adds only the members missing, never makes a team twice and never takes anybody out of one.
- **More ways to sign in**: several sign-in providers at once, each its own button on the sign-in page, with presets for Google, Microsoft Entra ID and GitHub (its organizations and teams count as groups). The single sign-on you had is the first of the list, unchanged.
- **LDAP and Active Directory**: people sign in with their directory name and password in the usual form, their groups making them administrators or users, nested Active Directory groups included. Over LDAPS or StartTLS; plain LDAP only if you allow it. Test the connection and look a person up from Settings.
- **Teams from groups**: map a provider's or directory's groups to teams (by name, or a regular expression), and people are put in them, and taken out again, at every sign-in. Teams you give by hand, or that a Portainer import gave, stay.
- **Two-factor sign-in**: set up an authenticator app from Account with a QR code, keep ten recovery codes, and a password alone no longer signs you in. Administrators can require it for everybody who signs in with a password, and reset a lost one under Users.
- **Freightdock speaks Norwegian**: every word of the UI comes from a catalogue, in English or Norsk bokmål, chosen per browser under Account, Language (or the browser's own language when it is one of them). Numbers, sizes, dates and times are written the language's way.
- **The agent is a repository of its own**, `freightdock-agent`, with its own image and releases; Freightdock builds against the commit of it it names, and the `docker run` line it gives for a new host names the agent image of the same tag.

### Changed
- **Freightdock's own certificate names the host**: `localhost`, `127.0.0.1`, `::1`, the machine's name and every address it listens on, plus any you add with `FREIGHTDOCK_TLS_NAMES`, and is good for 825 days, so tools that check names (Node, curl, Claude Code) accept it once the CA is trusted. It is made again at a start when the host's names or addresses change or it has less than 30 days left. The old certificate without names is replaced on the first start; a certificate of your own (`FREIGHTDOCK_TLS_CERT`) is never touched, and Freightdock no longer makes one at that path when it is missing: it says so and stops.
- **Single sign-on signs you in to your own account**: the first time somebody signs in through the provider, they land in the local account of the same name instead of a second "(SSO)" one. A switch in the SSO settings turns this off for a provider whose users choose their own names.
- **Users who were not administrators keep what they had** as Helpdesk on every environment; people added from now on see no host until they are given a role.
- **Sign-ins and sign-outs are in the auth log**, no longer in the activity log, which is now about changes.
- **The server's log is in local time**, with the offset written: the zone `TZ` names (`-e TZ=Europe/Oslo` in Docker), else the machine's, so its lines match the clock you read them by.

### Security
- **Volumes, networks and images have owners too**: public, a team's or private, like containers. Standard and Read-only users see only theirs, what is shared with them and what the containers they can see use; a volume or network shared with a hidden container no longer gives away that container's name. What you make or pull is yours.
- **Security settings per environment**, as Portainer has them, on an environment or its group: refuse everybody below Environment administrator privileged mode, host paths (with an allow-list of folders), the host's network, PID, IPC and UTS namespaces, devices, extra capabilities, security options and sysctls, and, by a switch of its own, consoles. Every way a container comes to be is held to them: a container made or edited, a template, a stack deploy (each service of the file Compose resolves, as whoever deploys it, a webhook as its maker), a Swarm service or stack, through the UI, an API token or MCP. The refusal names the service and the setting, on the field. Everything stays allowed until an administrator says otherwise, with a recommended Locked down preset one click away.
- Backups are sealed with your passphrase (Argon2id and XChaCha20-Poly1305), so an archive in a bucket or a share gives nothing away, and a changed or cut-off archive does not open.
- A notification channel's token, password or signing key is sealed at rest and never sent back to the browser; a webhook can be signed (HMAC-SHA256) so its receiver knows it came from Freightdock.
- Passwords are Argon2id; sessions are kept as hashes, so a copy of the database signs nobody in; every change needs the session's CSRF token, and a change or a console from another site is refused.
- Five failed sign-ins in 15 minutes lock that address, and that name, for the rest of the window.
- The single sign-on client secret, and Git stacks' tokens, are sealed at rest with a key of its own in the data folder, and are never sent back to the browser.
- An agent joins with a token that is good once for a day and pins Freightdock's own certificate authority, so it is sent to no other server; from then on it uses a certificate of its own. Removing the environment, or giving it a new token, cuts its tunnel and its certificate opens nothing more.
- A TLS host's client key is sealed at rest like every other secret, and never written to disk in the clear.
- Webhook addresses are 32 random bytes kept only as a hash; every call is in the activity log, wrong addresses are rate limited by caller, and a webhook is refused while it runs and for 10 seconds after.
- Docker Compose and git run with an emptied environment: Freightdock's own settings never reach a `${...}` in a compose file, and a Git stack can only use https and http.
- Deploying a Swarm stack no longer reads Freightdock's own files or settings into the swarm: Docker's command line runs with an emptied environment, as Compose does, and a file whose secret, config, `env_file` or `extends` names a file on Freightdock's server is refused. Before, an Environment administrator of one swarm could copy Freightdock's keys or variables into it. Make the stack's secrets and configs on the Swarm pages and name them `external: true`.
- Portainer's access token is sealed at rest and never sent back; Freightdock only ever reads Portainer, follows no redirect with the token, and checks Portainer's certificate (a self-signed one is trusted by pasting it). Not checking it is a choice you make out loud, and it is in the activity log.
- A registry's password, token or secret key is sealed at rest and never sent back to the browser; only an administrator adds, changes or removes a registry, and each is in the activity log.
- A Swarm secret's value goes into the swarm once and never comes back out through Freightdock, not even to an administrator; the activity log notes its size only.
- Every API route is held to one permission table by one guard, and a route without a rule is refused, so a new one cannot forget its check; a test fails the build for any route without a rule. API tokens and MCP act with their owner's role, and a read-only token stays read-only.
- A disabled account stays out through single sign-on too; before, signing in through the provider enabled it again.
- A CSV export defuses a field a spreadsheet would run as a formula.
- The update badges no longer name, to Standard and Read-only users, the containers they cannot see that are switched to update themselves.
- A container's webhook and its automatic-update switch go when the container is removed or pruned, and follow it when it is renamed or edited under a new name, as its owner does. Before, they stayed with the name, so a later container of that name, somebody else's too, was recreated by the old address and updated by a switch nobody set for it.
- A console, an attach or a command in the container Freightdock itself runs in is an administrator's alone: it holds Freightdock's keys and database and the Docker socket, so it is every host's. Before, an Operator or an Environment administrator of the local host could open one there.
- A swarm's services, tasks, service logs and stacks are the administrators' for Standard and Read-only users, as a project started elsewhere is: their lists are empty for them and one service or stack is not there. Before, those users read every service's variables, every task's logs and a stack's kept Compose file, though the same containers were hidden from them.
- Exporting an image is an Environment administrator's, as a volume's files are: an export is every file in every layer, credentials baked in included. Before, anybody with a role on the host could download any image whole, a read-only token too.
- **A single sign-on is finished only in the browser that started it**: what it needs on its way back is sealed into a short-lived cookie of that browser's, not kept on the server. Before, a sign-in address someone captured after signing in as themselves could sign somebody else's browser in to their account, and anybody could start enough sign-ins to close single sign-on to everybody for ten minutes.
- **One account cannot keep everybody else from the two-factor step**: an account has at most five sign-ins waiting for a code, its oldest giving way. Before, one right password sent again and again filled the store and turned away every other person's code step.
- **Signing in by the same name takes only that very name**: a name from a sign-in provider or a directory that a local account could not have (a control character, spaces at the ends, more than 64 characters) is turned away instead of trimmed and cut to fit, since the name it was cut to could be somebody else's account. An unverified e-mail address is no longer taken as a name, and a sign-in whose groups say less never takes the last administrator away.
- **A sign-in provider's addresses must be https** (or http to this machine), every one its discovery document names, and Account follows only an http or https address to link or sign out. Before, a provider that named a `javascript:` address could run script in Freightdock's page when somebody linked their account.
- **Too many connections to an agent's host no longer cut it off**: past 384 at once, the next one fails on its own and the tunnel carries on. Before, the 513th (513 log views held open by one user with Read would do) ended the tunnel, every console, log and deploy through it, and marked the host down.
- **A revoked agent never gets its tunnel back in a race**: an agent let in just before its environment was removed or given a new join token is cut once its tunnel is set up, instead of serving the environment (or the next one given its id). A TLS host edited or removed while its connection is being made is held to the same rule.
- **The environments' sockets never go in a folder somebody else made**: when the data folder is too deep for a socket's address, the short folder in the system's temporary folder is a new one with a random name, made by Freightdock alone. Before, its name could be worked out from the data folder's, and a folder another user of the machine made there first was taken as it was.
- Sign-in providers' client secrets, directory bind passwords and TOTP seeds are sealed at rest and never sent back to the browser; recovery codes are kept as hashes. A sign-in that comes back from one provider on another's callback is refused, a code from a TOTP app is good once, and wrong codes count against the same sign-in limit as wrong passwords. Names typed for a directory are escaped, so they cannot change what is searched for, and an empty password is never sent to it.
- **The update check and sign-in pictures read a host's answer only up to a size**: a manifest or an index up to 4 MiB, a registry's token answer up to 64 KiB, a picture up to 1 MB, each refused as soon as it passes the limit. Before, a registry an image named (anybody who can pull or build can name one) could send the server an answer as large as it liked, and the whole of it was kept and parsed.
- **The update check goes only where a registry should**: it follows a redirect only on the registry's own host, follows a token realm only over https and not to this machine, a private network or a cloud's metadata address (unless the registry is there too), and refuses a reference whose path steps out of the registry's API. Before, a registry an image named could have the server ask any address it liked and read the answer's status back in the update badge. A sign-in picture's redirect is followed only over https as well.
- **What an environment's Docker sends is held to a size**: a whole answer to 64 MiB, a Swarm service's log frame to 1 MiB, and the health and stats passes that ask every environment read through the same limit. Before, an agent's host (whoever may make containers there is root on it) could make the one server that manages every environment keep as much as its link carried, every 30 seconds and for every page following a service's logs.
- **Docker's events and stats are read a line at a time, to a limit**: a line that never ends is refused at 1 MiB, and each byte is looked at once. Before, bollard's reader kept such a line however long it got and parsed all of it again at every read, so an environment's Docker could make the server's notifications watch, and every events or stats page, use memory without limit and time growing with the square of what it sent.
- Removing an environment takes its stacks' folders off the disk with it, and a new stack always starts in an empty folder: stack ids can come again, and a new stack (anybody's, on any environment) could read the files a removed one left, its `.env` and Git clone too.
- A Git stack's saved token stays with the host it was saved for: moving the repository's address to another scheme, host or port needs the token given again (or cleared), checked before anything is sent. Before, the old token went to the new address, so whoever could edit the stack could have it sent to a host of their own.
- A Git stack's repository can no longer lead Freightdock out of its clone: git checks links out as plain files (`core.symlinks=false`), and a stack's compose file and `.env` are read, checked and deployed only when they lie in the stack's own folder once every link is followed. Before, a committed link at the compose file's path let whoever made the stack read any text file Freightdock could, other stacks' variables and its own keys too.
- A stack's compose file may make Compose read only files in the stack's own folder: an `env_file`, `label_file`, `include`, `extends` file, build context, Dockerfile, extra build context, SSH key, local build cache, or config or secret `file` that leads anywhere else (another stack's `.env`, a file on the server) is refused before Compose runs, when the stack is saved and before every job. Before, a Standard user on any one environment could read other stacks' variables, on every environment, through the Environment tab, and a build could have sent the data folder to their host.
- A Compose project started elsewhere has its files read where its labels say only for a Freightdock administrator, only on the local Docker, and never from Freightdock's own data folder; anybody else, and any other host, pastes the compose file to adopt it. Labels are whatever made the containers says, so before, anybody who could make a container on any host (or the host itself) could have Freightdock read and return another stack's compose file and `.env` to a Helpdesk user of that host.
- A Standard user's new stack (from the editor, Git or a template) may not take the name of a Compose project Docker already runs on that host. A container with no owner of its own belongs as its project's stack does, so before, a stack named after the administrators' external project made its containers (their variables too) the Standard user's to read, stop and remove.
- A restore no longer follows links when it makes the restored files private: a link a Git stack's repository committed could have pointed it at any folder on Freightdock's side and taken the execute bits off what is there.
- Sign-in tries sent all at once are held to five per 15 minutes too: each password or code try is counted as it starts, not after it was checked, when a burst of them could all be checked before the first was counted.
- A sign-in with a name longer than any account can have is turned away before it is counted or logged, and the auth log keeps a year: before, every failed sign-in could add up to 2 MiB of name to the database for good.
- Changing your password in Account is held to the sign-in limit, and every wrong current password is in the auth log: before, somebody with only your session could guess your password there as fast as the server checked them, with no trace.
- A new password revokes the person's API tokens, whether they change it in Account or an administrator gives one: before, a token left behind by whoever held the account kept working after it was taken back.
- **The first run asks for a setup token**, which Freightdock prints to its log as it starts (or takes from `FREIGHTDOCK_SETUP_TOKEN`): before, a web page that pointed a name of its own at a Freightdock not yet set up could make itself the first administrator through your browser.
- Freightdock can no longer be shown in a frame on another page, and says so in every answer (a Content-Security-Policy with `frame-ancestors 'none'` and scripts from Freightdock alone, `X-Frame-Options`, `nosniff`, a same-origin referrer); API answers are kept by no cache. Before, a page on a sibling name could frame a signed-in Freightdock and steer your clicks.
- A request whose body stops coming for 15 seconds is turned away and its connection let go: before, 1024 connections that sent a request's start and then nothing kept everybody else out, with no sign-in needed.

### Stability
- A webhook whose caller hangs up before the redeploy ends, or an edit, recreate or update whose page goes away, still runs to its end: the old container is no longer left stopped under another name, and the webhook no longer answers "running" until Freightdock restarts.

### Removed
- **Freightdock is now the UI of a Freightdock cluster, and only that**: the pages for one Docker host (containers, images, volumes, networks, events, the console), Home with its list of hosts, agents and TLS hosts, Swarm, Freightdock's own stacks, app templates, webhooks, registries, image updates, notifications, resource history, backups, the MCP server and the import from Portainer are gone. A one-node cluster does all a single host did, so there is one product to keep right instead of two; what of them comes back comes through the managers.
- **Roles per environment, ownership and security settings**: an Administrator changes the cluster, anybody else signed in reads it, until finer roles come with what needs them.
- **The Docker socket, the agent port 7444 and the Docker CLI and Compose in the image**: the UI talks to the managers only.
